# 局域网输入同步独立模块设计

状态：设计草案；已确定 LiteNetLib、局域网配对、同步最终 Xbox 状态、一对多、集成工作台面板。本文件不代表功能已实现或性能已验证。

## 1. 目标与范围

一台 Windows 电脑捕获键鼠并完成手柄映射，在本机输出的同时，让局域网内运行相同软件的多台电脑输出对应的虚拟 Xbox 手柄状态。复用当前 Controller 1/2、ViGEm 后端和程序化动作接口。

第一版采用单主发送、多接收拓扑；每台设备同一时刻选择关闭、发送或接收。接收端不转发收到的状态，避免网络回路。两手柄默认按 1→1、2→2 路由，可对每个接收设备分别勾选。

同步的是输入，不保证角色坐标一致：碰撞、帧率、游戏状态与网络同步会使人物位置产生差异。位置纠偏属于后续导航组件。

首版不包含屏幕串流、原始键鼠远控、互联网穿透、震动回传或配置文件自动复制。

## 2. 独立模块与部署选择

建议目录（均为拟新增，不在设计阶段创建工程）：

```text
auto_modules/
  lan_input_sync/
    README.md
    src/
      LanInputSync.Contracts/          # 不依赖手柄宿主的协议类型与接口
      LanInputSync.Core/               # 配对、会话、路由、权限、失联状态机
      LanInputSync.Transport.LiteNetLib/ # UDP 发现与实时传输
      LanInputSync.Security/           # TLS 认证、会话密钥、凭据存储接口
    tests/                            # 状态机、网络故障、性能集成验证
    docs/protocol-v1.md
  virtual_gamepad/host/src/VirtualGamepadHost/
    Integration/LanSync/              # 宿主类型转换、输入所有权、输出接入
  gui/gamepad/
    sync_panel.py                     # 工作台设备同步面板
```

推荐“独立类库 + 现有宿主加载”。网络线程与报告线程分开，代码可独立编译测试，实时数据不增加一次跨进程传输。工作台的统一启动入口继续负责启动宿主。

另一种部署是额外 SyncHost.exe，通过本地 IPC 连接手柄宿主；它的崩溃隔离更强，但多一套启动、提权、连接和退出流程。当前暂不选择，模块契约预留以后换用该部署的能力。

依赖方向：手柄宿主集成层依赖同步模块；同步模块不引用 VirtualGamepadHost、PySide6、游戏导航或 OCR。Contracts 先只定义实际需要的 Gamepad 状态载荷和会话接口，不提前构建任意远程命令执行平台。

LiteNetLib 使用固定 NuGet 发布版本 2.1.4，保留 MIT 许可证声明；不追踪 master。它负责传输，不自动提供设备身份认证或安全配对。依赖升级必须通过协议与故障回归。

## 3. 接入现有数据流

```text
键鼠映射 / core.actions 程序输出
  → 本地 StateStore 合并 + SafetyController
  → 同一份有效输出快照
       ├→ 本机 ViGEm Submit
       └→ IControllerStatePublisher → 有界发送缓冲 → 局域网

局域网
  → 认证、会话版本、顺序、权限检查
  → IRemoteControllerSink
  → 宿主输入所有权选择 → ViGEm Submit

PySide6 同步面板 ↔ 现有本机 Named Pipe ↔ 同步服务管理接口
```

现有 ReportLoop 默认周期为 8ms；ControllerRegistry.SubmitAll 当前按槽位读取 StateStore 并直接提交。接入时每槽位只采样一次，将相同状态交给本机后端和发布器。发布器只能做有界内存入队，不能在报告线程、StateStore 锁或输入钩子内等待网络、加密或磁盘。

本地程序通过现有 VirtualGamepadActionAdapter 输出的手柄动作也能被同步。导出仅针对本地来源且处于有效运行状态的输出；远程来源禁止再导出。

接收端不能直接调用现有 Safety.Start 来启用键鼠捕获。需要为每个槽位引入独立的输出所有权：Local / Remote，以及本地映射开关、远程接收许可。接收态可输出手柄，但原始键鼠保持正常透传。

建议给远程状态单独缓冲，由输出选择器选择本地 Store 或远程缓冲。不要把远程状态直接混进目前按“按钮 OR / 轴最大幅值”合并的本地 Store，否则本地自动化可能覆盖远程摇杆。Remote 占有期间，对该槽位的本地程序写入返回明确的 slot_owned_by_remote；切换所有权时清空旧来源并先输出中立状态。不同槽位可以有不同所有者。

## 4. 公开契约

| 契约 | 职责 |
|---|---|
| DeviceIdentity / PeerInfo | 稳定设备 ID、名称、协议版本、能力与可用地址 |
| ControllerSnapshot | 按钮位图、双扳机、四轴、来源槽位、输出是否启用 |
| SyncSession / Route | 主设备身份、接收设备、槽位映射、权限与本次会话代次 |
| IControllerStatePublisher | 接收本地有效输出，不阻塞调用者 |
| IRemoteControllerSink | 有权限地应用远程输出、释放路由；具体 ViGEm 由宿主实现 |
| ISyncService | 发现、配对、撤销、配置、启停、状态查询 |
| SyncMetrics | RTT、抖动、丢包估计、队列长度、回中原因、会话错误 |

传输层可以替换，数据层与配对/失联状态机不绑定 LiteNetLib API。模块必须能使用内存端点和假时钟测试，不依赖真实驱动。

## 5. 通道与消息

使用两个用途明确的通道：

1. TLS TCP 控制连接：配对、身份校验、权限、路由、开始/停止、会话密钥与健康探测。使用 .NET SslStream，不再另建一套 UDP 可靠管理通道。
2. LiteNetLib UDP 实时连接：模拟量完整快照使用 Sequenced；按钮变化记录使用独立 ReliableOrdered 通道。两类实时载荷均使用经过认证的会话加密。

控制连接关闭必须使对应实时会话失效。UDP 建连字符串、UDP 地址或设备名均不作为认证凭据。发现广播只用于展示候选设备。

实时头部包含 protocolVersion、sessionId、epoch、routeId、packetSequence、buttonRevision；载荷数值范围固定并校验。接收方先认证再改变状态或刷新存活时间。最大报文与队列长度受限，首版状态帧无需分片。

默认以与宿主一致的 125Hz 发布有效快照，提供 60Hz 省资源设置。Windows 定时器并非实时保证，必须测实际发送间隔。网络队列按接收设备独立管理，每条路由模拟量只留最新帧，慢设备不阻塞其他设备或本机。

### 快速点按不能只依赖最新快照

单纯丢弃旧快照，会在一次丢包中丢掉完整的短按。发送器必须比较每一次本地有效输出，在按钮位图发生变化时产生带递增 revision 的完整按钮位图记录。记录走可靠有序通道，模拟量快照同时携带当前 revision 用于一致性检查。

接收器按 revision 去重、顺序提交按钮变化；快照不能绕过尚未处理的按钮记录直接覆盖按钮位图。正常情况下在下一个本机报告周期输出变化；同批次收到 down/up 也至少分开一次实际后端提交，不能在提交前把两者合并掉。这保证“源端确实提交过的短按”到达接收后不会被接收缓冲吞掉，但不能保证游戏采样到任意短脉冲。

按钮记录具有有界积压预算（初始 200ms，待实测调整）。队列溢出、记录缺口长期未解决、健康探测超时，都终止该路由并回中；不在恢复后补执行一长串过时按钮。重建会话丢弃旧记录，从新快照基线开始。模拟量始终采用最新有效状态。

需要同时验证可靠记录对短按的恢复能力和它在坏网络下引入的尾延迟。无法兼得无限重试与固定实时延迟，本设计在超过预算时选择暂停并明确报告。

## 6. 配对与会话安全

接收端主动进入限时配对状态，显示临时设备码。主机在面板发现目标、输入码，双方确认后保存设备证书指纹。设备码用于定位/发起配对，不能单独当成长期密码或 AES 密钥。

首次没有受信任证书，不能仅对任意自签名 TLS 证书放行后就保存。配对界面须同时显示本次握手双方身份绑定的校验指纹，让用户在两台设备核对后确认；临时连接只允许配对消息，校验完成前无输入权限。详细协议实现前须定稿这一握手和校验信息，覆盖中间人替换证书测试。后续连接严格固定双方身份；证书变化必须重新配对。

认证完成的 TLS 会话分配每方向独立的随机 UDP 会话密钥与唯一 nonce 前缀。使用 .NET AES-GCM，nonce 由会话前缀和不回绕计数组成；重连生成新密钥。路由、epoch、序号均加入认证附加数据，认证后做重放窗口检查。ReliableOrdered 的正常重传去重不能导致重复动作。

管理和实时连接绑定同一身份与会话。不能通过重放、伪造心跳或另一设备的数据维持输入存活。频率限制、报文上限、未认证连接上限属于模块协议限制。

设备 ID 与私钥首次在每台电脑本地生成，不能随软件配置打包复制，否则会产生重复身份。偏好配置、可信设备列表和受 Windows 当前用户保护的私钥分别存储；日志不记录设备码或密钥。

仅在用户启用局域网功能后监听选定私有网络接口，发现同时提供手动局域网地址兜底。防火墙规则限制到选定程序/端口、专用网络与本地子网。访客 Wi-Fi 的客户端隔离可能阻止发现与直连，面板应给出明确连接失败信息。

## 7. 生命周期与按键释放

连接可信和允许输出是两个状态。软件可随工作台启动加载模块、记住配对和设备选择，但每次启动默认关闭同步输出；网络重连不自动恢复控制。

接收端状态：Disabled → Ready → Receiving → Suspended；F9 进入 EmergencyStopped。开始会话需要接收端本地许可和新的 epoch。暂停/失联/撤销使旧 epoch 永久失效，迟到 UDP 或可靠控制消息不能重新启用。

| 触发 | 行为 |
|---|---|
| 主端 F7/F8 暂停 | 本地对应槽位回中；远端收到禁用状态/控制通知后释放，保留配对 |
| 主端 F7/F8 恢复 | 在接收端仍许可的健康会话内重新协商对应槽位代次 |
| 接收端 F7/F8 | 暂停/重新授权对应远程槽位，不激活其本地键鼠映射 |
| 任一接收端 F9 | 本机全部回中并撤销远程输出许可；主端不能自动解除 |
| 主端 F9 / 停止同步 | 本机按原语义处理，向所有接收端发送停止，失效对应会话 |
| 控制连接断开 / 有效状态失联 | 本机回中、丢弃待处理按钮、挂起远程会话 |
| 撤销设备 / 更换所有者 | 先失效会话并归零，再移除凭据/切换路由 |
| 工作台关闭 | 管理器先关闭本次同步输出并回中，再按现有所有权规则退出宿主 |

有效状态失联阈值初始 200ms，用接收机单调时钟计时；控制心跳不能替代状态刷新。另用带挑战/回执的健康探测检测可靠数据长期排队，不仅依据收到旧帧的时间。初始探测周期 50ms、最大未确认预算 200ms，均须故障测试后定值。

立即回中仅指接收端处理到停止之后；突然断网必须等待失联检测，并叠加下一个实际报告周期。用本地独立看门狗确保网络处理停顿时也能撤销网络输出；宿主进程整体崩溃则验证驱动断开行为，不能靠同进程看门狗保证。

## 8. 面板与配置

现有虚拟手柄页面增加“设备同步”子页，保留手柄视图布局。同步子页包含：角色（关闭/发送/接收）、本机名称、配对码/确认、设备发现、可信设备列表、每台设备的 C1/C2 勾选、开始/停止、接收允许开关、在线状态、RTT/抖动/丢包与失败原因。

手柄页显示每槽位由本地还是远程控制，避免把“已连接”误当成“正在接收”。远程所有权下本地绑定可以查看，但本地输出不可悄悄混入。网络状态刷新可用 5–10Hz，不影响 125Hz 实时通道。

面板通过现有仅本机 Named Pipe 扩展 sync.* 管理命令调用 ISyncService。远程网络不能直接访问 CommandRouter 的任意本地动作接口。UI 线程不承担发现、配对阻塞、网络轮询或心跳。

网络偏好另存独立 lan-sync 配置：本机名、接口、角色偏好、目标设备、槽位路由、更新率、超时。已有 controller-1/2.json 不改结构。临时接收许可、epoch、会话密钥不持久化；磁盘更新采用原子写入。

## 9. 性能与验证

先前给出的有线 1–3ms / Wi-Fi 3–12ms 只是估计，不是测量结果或验收承诺。125Hz 对应名义 8ms 报告周期，仅能降低采样等待，不等于端到端 8ms。

指标区分网络 RTT、源输出到目的宿主接收、目的接收到 ViGEm 提交、以及游戏可见响应。不同电脑单向计时需要时钟偏移估计并报告误差，不能直接相减系统时间戳，也不能将 RTT/2 当成精确单向延迟。

初步验收目标：有线空闲 LAN 下，源端有效报告到目的后端提交的额外延迟 p95 ≤20ms；p99、最大值、CPU、内存与长期漂移全部报告。测试 1、2、4 个接收端；更多设备按实测结果扩展，不宣传无限数量。有线达到目标后再测实际 Wi-Fi，记录环境和差异。

验证层次：

1. 纯模块/假时钟：W+D 释放任意一键、短按、按钮序号/重放、乱序、跨通道先后顺序、溢出、pause→resume、旧 epoch、F9 后迟到消息、所有权切换。
2. 回环多实例：真实 TLS + LiteNetLib，测试发现、配对、证书替换、密钥轮换、坏帧和多个慢接收端。确认 ReportLoop 与 UI 不被网络阻塞。
3. 故障注入：1%/5% 丢包、乱序、重复、延迟、连续断网、网络线程卡住、控制连接假活、源端退出/接收端退出。静默断网回中目标为阈值加报告调度余量，统计实际最大值。
4. 两台真实 Windows + 游戏聚焦：分别验证 C1/C2、短按、摇杆、扳机、程序输出同步、源端吞键、接收端本地键鼠不被吞、暂停/关闭解锁；实际拔网线/禁用网卡验证回中。
5. 两小时持续运行和四接收端压力检查。日志持续记录指标聚合而非逐帧刷盘。

只有前三项通过不能声称已在游戏中验证；短按测试既检查实际 ViGEm 提交序列，也检查目标游戏是否采样到。

## 10. 分阶段交付

1. Contracts/Core、所有权与失联状态机；用内存传输验证组合和生命周期。
2. LiteNetLib/TLS/身份配对与完整状态传输；完善按钮记录、鉴权、epoch、故障注入。
3. 手柄宿主适配与现有工作台子页；验证双手柄和程序动作共用发布出口。
4. 双机游戏与多接收端实测，按测量结果调整周期、超时和缓冲；输出性能报告后再确定默认值。

当前交付仅设计文档；尚未安装依赖、修改宿主/面板、开放网络端口或启动同步服务。
